# Roadmap

## Phase 0: Contract & Boundary

- define stable domain contracts
- define Core-owned versus Personal Growth-owned state
- define execution attribution
- verify integration points against the target branch
- add tests before broad implementation

## Phase 1: Execution Foundation

- goals
- objectives
- task references and milestones
- execution outcome references
- evidence references
- execution attribution
- persistent domain state

## Phase 2: Learning & Assessment

- skill model
- learning objectives
- assisted / guided / independent modes
- blind transfer
- fragile-skill detection
- evidence quality rules

## Phase 3: Domain Critic

- user progress critique
- capability/evidence discrepancy detection
- domain-relevant agent/output critique
- actionable recommendations
- route recommendations back through Core task boundaries

Core remains responsible for runtime execution-quality critique, trajectory supervision, verification, and safety signals.

## Phase 4: Governance

- autonomy policy integration
- approval integration
- social/streaming access policy
- audit trail

Personal Growth provides domain context; Core enforces execution-time autonomy and approval.

## Phase 5: Career Intelligence

- skill-to-market mapping
- skill gaps
- opportunity research
- portfolio evidence

Reuse existing Abelink research capabilities instead of creating a duplicate research runtime.

## Phase 6: Education & Scholarship

- university/program tracking
- scholarship tracking
- requirement matrix
- evidence gap analysis
- deadline planning

## Phase 7: Lightweight Learning from Outcomes

- inspect historical execution outcomes
- identify recurring learning/evidence gaps
- derive lightweight user preferences where useful
- identify recurring domain failure patterns

This phase MUST NOT become a persistent strategy ontology, evolutionary strategy engine, learned policy model, or replacement for Core trajectory supervision.

## Phase 8: Optimization & Validation

- reduce unnecessary interaction
- improve evidence quality and verification handoff
- improve policy routing
- benchmark human-capability outcomes and agent execution quality
- compare architecture changes using the same model/task/tool conditions where possible

## Implementation Guardrails

1. Do not create a second agent runtime.
2. Do not duplicate Core trajectory or verification state.
3. Do not couple contracts to volatile implementation file names.
4. Do not infer human mastery from AI completion alone.
5. Keep attribution simple unless evidence demonstrates a need for more complexity.
6. Prefer stable contracts and tests over framework-building.
